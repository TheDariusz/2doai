Product and architectural drivers

2do AI is designed for work that ordinary todo applications forget: current tasks, long-term goals, and dreams all live across 11 life domains, while an AI partner remembers context and returns with a useful proposal at a natural, non-fixed moment.

Representative target flow. A user records a dream about visiting Japan. The system retains the item and relevant personal context. After a non-fixed interval, the backend selects the neglected dream, asks the AI to formulate a concrete first-step proposal, sends it by email, and keeps it available in the application until the user responds. Every step of that sentence is now implemented, S-05 having supplied the two that were missing: the non-fixed interval that starts the flow, and the email that carries it. Delivery in production additionally needed a verified sender domain at the mail provider — configuration rather than code, and it was completed on 2026-09-02: a forced cycle against production delivered a real message and left the same proposal waiting in the application (deployment runbook, phase 8.4). implemented
Product differentiator
Proactive returns in a natural rhythm, not another fixed-time reminder scheduler.
Memory requirement
Structured profile facts plus an episodic log let proposals refer to the user's real history.
Guardrails
Per-user privacy, durable data, and explicit account erasure are architectural requirements from the start.
Deliberate scale
1–10 users, less than 1 QPS, and less than 1 GB justify one small backend and managed infrastructure.

Frontend status

A React 19 single-page application on react-router. Session bootstrap, login, registration, logout, account deletion and the 11-domain navigation shell all consume the API through one CSRF-aware client; the /api development proxy and production reverse proxy are implemented. Per-domain pages are still placeholders, and PWA behavior is planned.

The /goals screen adds the first data UI. Current tasks, goals and dreams are created, edited, converted between layers, completed, reopened and deleted against the live API, and narrowed by layer and by category. Above that list sits the proposal card (S-04b): one button asks the backend for something to come back to, the returned card carries the AI's sentence and the four answers, and STARTING renders the generated bullets, each saveable as a current task with one click.

Since S-05 the card no longer waits for that button. On mount it reads GET /api/proposals/pending, so a proposal the rhythm opened overnight is on screen when the user arrives — which is what makes the emailed nudge a nudge rather than the delivery. That read deliberately stays quiet: nobody asked for it, so a failure is recorded in the console instead of raising a banner about something the user did not cause, and 204 leaves the idle screen exactly as it looks before anyone asks anything.

Four decisions that shaped it

Filters live in the URL
Layer, category and withdrawn are held in the query string and applied in the browser, so a reload or a shared link restores the view and GET /api/goals still publishes no query parameters — the deliberate choice at single-user scale. Uncategorised entries are their own filter choice rather than a gap, matching the selection engine's treatment of a null category as one shared bucket.
Routes stay English and lowercase
/goals, /domain/inner_growth, ?layer=task. The interface is localised; the URL is not, and the SCREAMING_CASE stays on the wire where the enums live.
Withdrawal is a filter value, not a route
Withdrawn entries are hidden by default and reached through a third control in the same filter row. Restore is the same PUT the edit form already uses, so withdrawal is reversible rather than a delete.
An empty list must say why
A URL naming a layer that does not exist falls back to showing everything, and a combination matching nothing says so — an empty list must never read as “you have no entries”, the same lie the load-failure banner exists to avoid. The message triggers on an empty visible list rather than on “a filter is set”, because the withdrawn filter is the first one that is on by default: the old condition would have shown a user whose only entry is withdrawn the blank screen of a brand-new account.

These projects build independently; there is no root workspace. Local setup and execution belong in the root README. Product and architecture intent remain canonical in the PRD, roadmap, and data model.

System context and containers

Current runtime implemented

Pattern B — unified origin: Cloudflare Pages serves the static frontend and reverse-proxies /api/* to the Fly.io backend, so production is same-origin and needs no CORS. Sessions are server-side cookies held in-memory on the single Fly machine (not JWT, never DB-backed — a per-request session SELECT would defeat Neon autosuspend).

The browser receives the React single-page application from Cloudflare. API requests cross the same public origin through a Pages Function, reach one Spring Boot machine, and use PostgreSQL only when application data is needed. GitHub Actions is the delivery plane, not a runtime component.

The production proxy is frontend/functions/api/[[path]].ts; local development mirrors it in frontend/vite.config.ts.

Backend design implemented

Base package com.thedariusz.todoai, one package per domain slice. Aggregates use UUID v7 surrogate PKs (@UuidGenerator(style = VERSION_7)). Mutable domain tables use created_at and updated_at; append-only event tables may omit updated_at. Static reference tables may use a natural key and omit audit columns.

Terms used below

The diagrams mix product language with implementation names. These definitions establish the domain meaning before showing the classes that implement it.

Account
The user's complete presence in 2do AI: sign-in identity plus every item, memory record, and proposal they own. Account deletion means erasing that whole set, not only login details.
User
The persisted identity and credential owner stored in app_user. A user owns exactly one account's data and one AI-memory root.
Session
The authenticated login state held in backend memory and referenced by the browser's session cookie. It is not the user's durable application data.
Category
One fixed life-domain classification, such as HEALTH or FINANCE. The database category row and Java LifeDomain enum represent the same set.
Goal
A long-term intention the user commits to, carrying a horizon of either this year or the coming months. Stored in the goal table with layer = GOAL.
Dream
A someday aspiration with no timeframe — the same goal table with layer = DREAM and no horizon. One aggregate serves all three layers because every later slice consumes the union and nothing but the time fields differ. Converting one layer into another is an ordinary edit, not a move between tables.
Task
A current, concrete action — the same goal table with layer = TASK, no horizon, and an optional due_date. A task is the only layer that may carry a due date, and the only time field a task may carry.
Proposal
One entry the system brings back to the user because it has been neglected, together with the sentence it was phrased into and whatever the user answered. It is a stored row, not a computed reply: a user has at most one pending proposal at a time, and pressing the button again returns that one rather than paying for a second model call. Since S-05 a proposal also arrives without anyone pressing anything.
Natural rhythm
The non-fixed cycle that decides when the app comes back on its own (FR-011): a moment drawn uniformly 2–7 days ahead, landing inside daytime hours, redrawn after every fire. Random rather than periodic on purpose — a fixed cadence is the alarm clock this product exists not to be, and the unpredictability is a product feel, not a secret, which is why ProposalRhythm takes an ordinary unseeded Random.
Quiet hours
The part of the day the rhythm will not fire in. ProposalRhythm.next never draws outside it, so the guard exists for the moments that arrive late — a machine down across a whole window comes back holding a fire time already past, and that one waits for the window to reopen rather than landing at 04:00. Bounds are configuration (proposal.rhythm.window-start-hour / window-end-hour), read in the user's zone for the same reason due_date is.
Superseding
What the machine does to a proposal the user never answered when the next cycle arrives: ProposalAnswer.SUPERSEDED closes it and its entry is quieted for the same few days a spoken “not now” buys. It is an answer written by the app rather than the user — ignoring a proposal is a response to it — and it is kept a distinct value, and a distinct memory episode, precisely so the next prompt can tell “they said not now” from “they said nothing at all”. The scheduled path supersedes; the manual button never does, because a second press must return the same card rather than replace it.
Snooze
A date before which an entry is not proposed again, held in goal.remind_after. Three of the four answers write it and differ only in the term they pick — a short default for “not now”, a week after “starting”, and 7, 30 or 90 days when the user names one. One mechanism, three defaults.
Withdrawal
The fourth answer: the user says they will never act on this entry, and it leaves the running without being deleted (goal.withdrawn_at). Reversible — the entry is reachable through its own filter and restored by an ordinary edit, which is what separates it from DELETE /api/goals/{id}.
First step
The 3–5 concrete actions the model returns when the user answers that they are starting. Generated once, stored as JSON on the proposal row, and offered to the user as tasks they may save with one click.
AI memory
The per-user aggregate that provides personal context to AI prompts. It contains durable profile facts and an append-only history of relevant events.
Profile fact
A durable, typed statement about the user, such as an occupation, value, or priority.
Episode
An append-only event in AI memory, such as a completed item or proposal outcome, stored with its occurrence time and structured JSON payload.
LLM port
The provider-neutral LlmClient interface used by backend use cases. Its Spring AI adapter translates those calls to the selected external model provider.

Architectural roles

The backend uses ports and adapters where a boundary benefits from substitution or modular ownership. It is deliberately pragmatic rather than a pure hexagonal architecture: Spring Data repository interfaces are framework-coupled persistence adapters, not domain-owned ports.

Inbound adapter
Translates an external trigger into an application call. REST controllers and security filters adapt HTTP and Spring Security events into the backend.
Application service
Coordinates one use case and its transaction, using domain objects and dependencies without owning HTTP or provider-specific behavior.
Outbound port
An application-owned interface describing a capability required from an external system. LlmClient and EmailSender are the two.
Outbound adapter
A technology-specific implementation of an outbound port. SpringAiLlmClient translates the LLM contract to Spring AI; SmtpEmailSender translates EmailSender to JavaMailSender.
Persistence adapter
A Spring Data repository interface whose generated implementation reads or writes PostgreSQL. It is a practical framework seam, but not a pure domain port.
Extension port
An internal SPI that lets another module contribute behavior. PerUserDataDeleter lets each user-owned module plug into account erasure.

goal

One aggregate carries all three layers, discriminated by layer. The layer × time-fields rule — only a goal has a horizon and it always has one, only a task may carry a due_date — is enforced at three depths: the request records return 422, the aggregate constructor and update throw for any future caller, and the chk_goal_layer_time_fields database constraint cannot be bypassed at all. No operation takes an owner from the client: findByIdAndUserId and deleteByIdAndUserId make another account's identifier and a nonexistent one answer with the same 404, and a foreign DELETE removes nothing.

S-04b added the two states an answer leaves behind — remind_after and withdrawn_at — here rather than on the proposal, because the user performed them. withdrawn joined GoalUpdate under the same full-replace rule completed already follows, which is what makes restore an ordinary PUT instead of a new endpoint. Both are primitives on that record, and Jackson 3 rejects an omitted primitive with a 400 rather than defaulting it to false — a loud failure the API test pins, since boxing the field later would quietly turn "withdraw this" into "leave it alone".

proposal

The proactive loop, end to end. It arrived in three parts and the seams are still visible in the code: S-04a built the deterministic pick, S-04b put a model in front of it, stored what the user was shown, and gave them four ways to answer — and S-05 removed the button, which is the part that makes this a product rather than a query.

Choosing the entry (S-04a)

Two rules run in order. Neglect decides who is eligible: an active entry qualifies once it has been idle for its layer's patience — 7 days for a task, 14 for a goal, 30 for a dream — or, for a task alone, once its due_date has passed — and a missed term ranks ahead of any amount of silence, so an overdue task is proposed before a merely idle entry. Balancing then decides who wins inside a tier (FR-012): ranking by raw idle time would hand every proposal to whichever life domain the user neglects hardest, so a domain is scored instead by how long the user has been silent in it — the idle time of its most recently touched entry, completed ones included — and the most silent domain goes first. Raw idle time is the second key outright, settling two equally silent domains as readily as two entries inside one. Entries with no category are not dropped; they share a single bucket rather than one each.

Balancing never suppresses a proposal, only reorders one. For a user active in all eleven domains every silence score ties, the first key goes constant, and the comparator collapses to raw idle time — the ranking balancing exists to avoid. It switches itself off rather than falling silent.

The engine is a pure function: it takes the entries and the current moment as arguments and holds no clock, no repository, and no LlmClient. That is what lets ProposalSelectorTest state the whole product rule without a container, and it is why this half ships before the AI half instead of with it. ProposalService reads through the existing user-scoped finder and adds none of its own — balancing needs the domains the user has been active in, which is exactly what a "find the neglected ones" query would filter away.

Two more inputs decide eligibility rather than ranking, and they are why the engine is still honest about time. A withdrawn entry is never proposed, and a snoozed one is not proposed before its date — but the silence map deliberately still counts a withdrawn entry, because withdrawing it was an interaction and dropping it from the map would hand its domain the next proposal the moment the user said "never".

Phrasing it, storing it, answering it (S-04b)

"Last interaction" is the entry's updated_at, which is honest only while the user is the sole writer of that row — so this half is built around not spoiling it. Everything the machine writes on its own (the phrased message, the frozen neglect count, the generated first step) lands on the proposal row; only what the user performed — the snooze, the withdrawal — is stamped onto goal. That split is the reason Proposal is an aggregate rather than four more columns on Goal.

At most one pending proposal (FR-018) is a schema invariant, not a service check: a partial unique index over proposal (user_id) WHERE answered_at IS NULL. The plan leans on the index precisely because a "does this user already have one?" read would race with itself on a double-click and store both — and when the insert loses that race, the service returns the proposal that won rather than a 500. A repeat press therefore returns the same card and costs no model call, which is what at-most-one means under a manual trigger.

The model never gets to fail the request. ProposalPrompt builds both conversations — the 2–3 sentence proposal, and the 3–5 bullet first step through completeStructured — and every LlmException has an answer waiting: phrasing falls back to ProposalTemplate, a deterministic sentence with no model in it, and the source column records which arm wrote the message so a demo can tell them apart. A failed first step still lets the answer land, with empty bullets. Neither path is dead code — the fallback is the roadmap's own contingency, permanently wired in rather than held in reserve.

Neither method is @Transactional, and that is deliberate. A Sonnet call has a 60-second budget, and a method-level transaction would pin a Hikari connection open for all of it — the exact idleness anti-pattern a metered, autosuspending Neon punishes. Phrasing runs with no transaction at all; answering calls the model first and then opens a TransactionTemplate around the three writes alone, so the entry's snooze or withdrawal, the proposal's answer and the memory episode land together or not at all.

The four answers are one endpoint, POST /api/proposals/{id}/answer, returning the same representation a proposal already has — one shape for the client to render whether it just asked for a proposal or just answered one. Three of them snooze the entry and differ only in the term; the fourth withdraws it. All four also write an episode into AI memory, which is what makes "every answer shapes what is proposed next" a mechanism rather than a promise: the next proposal's prompt reads that log. An id the caller does not own answers 404 rather than 403 — it must not be distinguishable from one that does not exist — a second answer is 409, and a term outside the offered set is 422 in both directions (missing when required, present when it would be silently dropped).

Coming back without being asked (S-05)

The schedule lives in memory, and that is the whole design. ProposalScheduler keeps a Map<UUID, OffsetDateTime> of when each account is next returned to, and a 60-second tick compares it against the clock. The obvious implementation — ask the database who is due — is the one thing this feature could not afford: Neon bills metered compute and suspends after roughly five idle minutes, so a query on every tick would hold the machine awake permanently for the roughly one fire per 2–7 days it exists to perform. The database is touched exactly three times: once at boot, once when an account registers, and once per actual fire. The liveness probe reads a field and nothing else, for the same reason — and the map is pushed at both ends of an account's life rather than polled: registration adds an entry through UserRegistered, deletion removes one through the PerUserDataDeleter seam FR-019 already fans out over, so no deleted account is ever discovered by spending a query on it.

The health endpoint is the other door into that bill, and it is the one that opens by accident. The liveness group is careful — it holds the scheduler's own pulse and nothing that touches the database — but plain /actuator/health is exposed, unauthenticated (Fly's probe reaches the liveness path through the same filter chain), and runs every registered contributor regardless of which group names it. So each contributor is not a diagnostic so much as work any anonymous request can make the app do: db costs a SELECT 1, and the mail starter would have added an SMTP handshake against the provider beside it. One uptime pinger on that URL would hold Neon awake around the clock — the same 24/7 wake-up the in-memory schedule exists to avoid, arriving through the health check instead of the tick. Hence management.health.mail.enabled=false, asserted by HealthProbeApiTest.

app_user.next_proposal_at is the map's only backup and it is enough. A restart reloads the stored moments rather than redrawing them, so the rhythm survives a deploy instead of bunching every account around one; the map is authoritative while the JVM lives, the column across its death. There is exactly one machine — fly.toml pins it — so there is nothing to elect and nothing to lock.

proposeScheduled is not propose() with an argument. The manual trigger short-circuits on a pending proposal, which is right under a button and wrong under a clock: doing it here would stop the rhythm dead the first time a user ignored a proposal — exactly the user this feature exists for. So the scheduled path replaces instead. Two orderings inside it are load-bearing. Selection runs first and superseding happens only if it produced something, because closing the old proposal is FR-018's implicit "not now" and that must not happen merely because the clock struck; and the ignored entry is excluded from the candidates, which is what stops the friend asking about the same thing twice in a row.

The email is sent inside the fire's catch, not after it. The next moment is drawn whatever happened — nothing to propose, a failure mid-cycle, a message that would not send — because leaving the old moment in place would make that account due again on the very next tick, turning the one path that must stay quiet into a query every 60 seconds. And because the proposal is stored before the message is attempted, a delivery failure costs the user the nudge and not the proposal: it stays pending and the card is waiting the next time they open the app. That is also why there is no retry queue — the app already has a second channel, and it is the reliable one.

The address rides along on the User row the fire already loaded for its vanished-account check, so reaching a user costs no query of its own. ProposalEmail writes the subject and body; it is Polish for the same reason ProposalTemplate is, and for no other — the message on the screen and the message in the inbox are both the sentence the user reads, while every instruction to the model stays English. The subject names the entry, abbreviated, so a week of proposals does not collapse into one mail thread.

One FK in this schema carries ON DELETE CASCADE: proposal.goal_id, so DELETE /api/goals/{id} keeps working while a proposal points at the entry. The cost is named rather than hidden, and it is charged twice. The “a missing deleter fails loudly on the FK” property does not protect this table: GoalDataDeleter runs during the same account erasure and every proposal has a goal, so the cascade would remove the rows whether or not ProposalDataDeleter exists — which is why the erasure is asserted directly in a test rather than trusted to the constraint. And because the two deleters share one transaction in an unspecified order, the cascade can take rows out from under a persistence context that has already loaded them; the proposal deleter therefore issues a bulk delete, which is immediate and order-independent, instead of the derived one.

AI communication in Spring Boot implemented

The backend communicates with an AI model through a normal Spring dependency: application code calls the provider-neutral LlmClient interface, its SpringAiLlmClient adapter creates a Spring AI prompt, and Spring AI performs the authenticated HTTP exchange with OpenRouter.

Current boundary. The port, adapter, configuration, unit tests, and an optional live OpenRouter round-trip are implemented, and ProposalService is the first production caller — it exercises both operations, free text for the proposal's wording and schema-constrained structured output for the first step, on prompts enriched from the user's AI memory (S-04b). Still planned: category auto-tagging at capture (S-09) and the background proposal cycle (S-05).

Configuration, privacy, and cost guardrails

  • spring.ai.openai.base-url=https://openrouter.ai/api/v1 points Spring AI's OpenAI client at the OpenRouter-compatible endpoint.
  • OPENROUTER_API_KEY is injected into spring.ai.openai.api-key. It is a Fly secret in production and never part of an LlmRequest, repository file, or application log.
  • Every free-text and structured request adds provider: { data_collection: "deny" }. This prevents routing to providers that collect data for training; OpenRouter dashboard privacy settings remain the operational half of the guardrail.
  • No-training is not the same promise as zero retention. The accepted decision allows normal API processing and prompt caching while prohibiting training on personal data.
  • Haiku and Sonnet slugs are configuration values. One gateway and one adapter support the split without creating a client per model.
  • Embeddings are disabled and there is no vector database in the MVP. The proposal prompts render bounded profile facts and recent episodes into ordinary prompt messages instead.
  • Stored, user-influenced content never reaches a prompt raw. The memory block and the entry's own words appear only inside a <data> block, the system message tells the model those blocks are data rather than instructions, and the fence tokens are stripped from the payload so nothing can close its block and keep writing outside it — the render-boundary discipline that also governs the AI code review's diff.

The one thing S-05 could not inherit is a poll. Neon bills idle compute and autosuspends after roughly five minutes, so anything touching the database more often than that pins the machine awake permanently — the scheduler computes its next fire time in memory and queries only when it actually fires, roughly once every two to seven days. A unit test asserts that literally: a tick with nothing due must reach neither repository. The other half of the same decision is the liveness indicator, which reports the tick's own pulse from a field rather than a query, so the failure this feature is uniquely exposed to — the thread dying while the web server keeps answering — becomes a Fly restart instead of silence.

Data architecture

Every user-owned aggregate carries an explicit owner boundary. The current model contains the user, fixed category reference data, the AI-memory aggregate, the goal table holding all three layers, and — since S-04b — the proposal table recording what the user was shown and what they answered. S-05 added the last missing piece as a single column rather than a table: app_user.next_proposal_at. Nothing in the data model still belongs only to the target diagram.

Ownership and isolation
AiMemory is one aggregate per user. Child profile facts and episodes are reached through that root.
Explicit erasure
No user_id FK carries ON DELETE CASCADE. Each module supplies a PerUserDataDeleter; the user row is deleted last so a missing module fails loudly. The one exception is proposal.goal_id, and it is named where it is declared.
Append-only episodes
Episodes record events that happened and therefore use created_at without pretending that history is mutable.
Schema ownership
Flyway migrations change PostgreSQL; Hibernate remains on ddl-auto=validate as a mapping drift guard.

Current model implemented

User identity, fixed categories, personal AI memory, the goal table and the proposal table are present. Profile facts are durable semantic statements; episodes are a bounded event history stored with a JSON payload. goal keeps its completion state as a nullable completed_at rather than a boolean, because the memory enrichment that reads it next needs to know when a thing was finished, not merely whether. The selection engine added no column and no index: it measures neglect from updated_at, which is only honest while the user remains the sole writer of a goal row — the day a background job stamps one, the engine needs a last_interaction_at of its own. S-04b was the first slice that had to answer that warning, and it took the first option rather than the column: remind_after and withdrawn_at sit on goal because the user asked for them, while everything the machine writes on its own lives on proposal. That table's own constraints are mostly product rules a service check could not hold — a partial unique index over (user_id) WHERE answered_at IS NULL is FR-018's at-most-one-pending rule, immune to the double-click a service-level read would race with; and goal_id is the schema's one ON DELETE CASCADE, so deleting an entry that carries a proposal still works, at the documented cost of that FK no longer guarding a forgotten deleter (which is also why that deleter issues a bulk delete rather than a derived one — the two run in one transaction in no fixed order). A third constraint is a backstop rather than a product rule: CHECK ((answer IS NULL) = (answered_at IS NULL)) keeps the answer pair whole, since the pending index reads only one of the two and a half-written answer would hold the slot for good while every reader called it answered. The other clock decision is due_date: it is a LocalDate the user picked off a calendar, so the engine reads its clock in the user's zone rather than the server's. There is no user.timezone column yet, so that zone is pinned to Europe/Warsaw in one line of ProposalService; a UTC comparison would leave a task that fell due at Polish midnight unflagged until 02:00, and the endpoint would answer 204 — the one place a real fault looks like a legitimate empty answer.

S-05's only schema change is app_user.next_proposal_at, and what is interesting about it is how little it is asked to do. It is not the schedule — the scheduler holds that in memory, because a column read on a timer is exactly the metered-idle cost Neon punishes. It is the schedule's backup: written once per fire, read once per boot, so a deploy resumes each account's moment instead of redrawing every one of them into a bunch. Nullable on purpose, and that null is a meaningful state rather than missing data — it says "never scheduled", which is what every account predating this slice is, and what the boot pass converts into a first drawn moment. It is also not a lease: it presumes the single machine fly.toml pins, and two schedulers over one column would each fire for every account.

Delivery and operations implemented

Five GitHub Actions workflows across two triggers. The two deployment workflows stay independent and path-filtered—a frontend-only change never redeploys the JVM and vice versa—but each is now split into a quality job that runs on both pull requests and master pushes, and a deploy job that declares needs: quality and runs only on push.

Current validation boundary. Every pull request runs a pull-request quality gate—backend tests, the frontend lint/test/build chain, repo-wide checks, dependency and secret scanning, and an AI code review—and a deploy cannot start until that same gate passes on the merge commit. Changes under docs/ are validated by repo-checks.yml but are not deployed by these workflows.
Why no workflow filters on paths:. A required status check whose workflow is filtered out never reports, so the pull request sits at “Expected — waiting for status to be reported” forever. Every workflow here therefore filters by path inside the job and always reports a result. Re-adding a trigger-level paths: or paths-ignore: to any required check silently converts “skip this PR” into “block this PR permanently”—a human can force-merge past it, but Dependabot cannot.

backend.yml

  • Two jobs: quality runs mvn -B test on pull requests and on master; deploy declares needs: quality and runs only on push.
  • No trigger-level paths: filter—a required check that never runs blocks the pull request forever, so path filtering moved into the job.
  • concurrency: deploy-backend, cancel-in-progress: false on the deploy job—deploys queue and do not cancel mid-flight. The quality job has its own per-ref group so pull requests never queue behind a deploy.
  • The workflow records the live Fly image before deploying. Rollback uses fly deploy --image <recorded-image>; expand-only migrations keep the older image compatible.
  • Trivy runs after mvn -B test, in the same job—this ordering is a correctness constraint, not a preference. Trivy re-implements Maven resolution and calls Maven Central live; against a cold ~/.m2 it hard-fails with 429 Too Many Requests, Retry-After: 1800 rather than degrading to a partial result. Running after the test suite leaves the cache warm, so resolution is offline-clean.

frontend.yml

  • Same split. Gate: npm ci && npm run lint && npm test && npm run build. The build is the typecheck—npm run build is tsc -b && vite build, and tsconfig.functions.json pulls the Cloudflare Pages /api/* proxy into that compile.
  • cancel-in-progress: true—only the newest frontend deploy matters.
  • Publishes frontend/dist to Cloudflare Pages.
  • Trivy reads package-lock.json directly; no npm install is needed for the scan.

Dependency scanning: report loudly, gate narrowly

Both quality jobs run Trivy twice. The first pass is informational (exit-code: 0): it renders a full table into $GITHUB_STEP_SUMMARY and uploads it as an artifact. The second reuses the first pass's binary and vulnerability database (skip-setup-trivy: true, so no second download) and is the one that can fail the build—restricted to severity: HIGH,CRITICAL with ignore-unfixed: true, because a finding with no available fix is noise a contributor cannot act on.

On the frontend the two passes deliberately see different dependency sets: the report includes devDependencies so build-time supply-chain risk stays visible, while the gate scans production dependencies only. A vulnerable test runner should be known about; it should not block a merge.

Config file, not an environment variable. Including dev dependencies requires .github/trivy-report.yaml: trivy-action exposes no matching input, and TRIVY_INCLUDE_DEV_DEPS is silently ignored—it reports 7 packages with the variable set and 272 with the real flag. A silently-ignored setting is worse than none, because the report looks like it covers dev dependencies when it does not.

repo-checks.yml

  • Checks belonging to neither side: the docs/index.html link and anchor test, and an assertion that backend/fly.toml still declares memory under [[vm]].
  • Repo-wide secret scanning via trivy fs --scanners secret. No longer the only secret detection here: the repository went public on 2026-08-03, which made GitHub's own secret scanning and push protection free, and both are now enabled. They are complementary—GitHub's is preventive but limited to known provider patterns, Trivy's is post-hoc but matches more shapes.
  • The secret scan sets TRIVY_OFFLINE_SCAN=true: a secret-only scan still runs the POM analyzer, and unlike the backend job there is no warm ~/.m2 here to save it from the same 429.
  • Runs the AI review's gate-predicate fixtures, so the one piece of genuinely new logic cannot rot unnoticed in a workflow that only fires on code changes.
  • Unfiltered by design—everything here runs in seconds.

ai-review.yml

A hand-rolled diff → OpenRouter → strict JSON schema → gate job, deliberately not an off-the-shelf reviewer. The model receives the diff as data and is given no tools, no shell, no filesystem and no network, so prompt injection inside a pull request caps out at producing a wrong finding rather than running a command. The system prompt declares everything between <diff> and </diff> untrusted third-party data whose instructions must never be followed—the same render-boundary discipline the project already requires for stored content reaching an LLM.

  • Two passes. The advisory pass covers correctness, performance, tests and maintainability and can never fail the check. The security pass is the only one that may exit non-zero.
  • The gate needs two independent keys, because severity alone costs a model nothing to inflate: it blocks only on category == "security" and severity == "high" and confidence >= 0.8.
  • Fails open on everything else. A 429, a 5xx, a timeout, malformed JSON, an empty body or a missing key logs a warning and exits 0. An OpenRouter outage must not block a merge at 11pm; only a successfully parsed finding may.
  • Findings post through the reviews API with event: COMMENT, never REQUEST_CHANGES—on a solo repository a bot requesting changes blocks your own merges until manually dismissed. The exit code is the enforcement; the comment is only the message.
  • Guarded against fork pull requests (no secrets), Dependabot (separate secrets store), and a skip-ai-review label. Diffs over ~1500 lines downgrade to advisory rather than gate on a review the model cannot hold.
  • Model choice is one repository variable, AI_REVIEW_MODELS, with a literal fallback—changing reviewer needs no commit. Both passes log the serving model and cost to the step summary, so a silent provider fallback cannot swap the reviewer unnoticed.

The workflow is inert until the OPENROUTER_CI_KEY secret exists: both passes warn “review skipped” and the check goes green. Setup and model-swap rules live in ai-provider.md.

Supply-chain hygiene

Every third-party action is pinned to a full 40-character commit SHA, with the human-readable tag as a trailing comment. This is not generic hygiene—it is the documented remediation for a real incident: in March 2026, 76 of 77 trivy-action tags were force-pushed to credential-stealing commits, and a tag is a mutable pointer that can be moved under you.

Pinning trades a tag-hijack risk for a staleness risk, since an immutable SHA never receives security fixes either. dependabot.yml is the counterweight: it understands SHA pins and bumps them together with their version comment. Its three ecosystems—github-actions at the repository root, npm under /frontend, maven under /backend—are each grouped into a single weekly pull request, capping the noise at three per week. Trivy and Dependabot are complementary rather than redundant: Trivy detects and fails the merge, Dependabot opens the pull request that fixes.

Findings that are genuinely unfixable or unreachable go in .trivyignore, and every entry carries an expiry (exp:YYYY-MM-DD). Once the date passes Trivy stops honouring the line and the gate goes red again, which forces a re-decision instead of letting a stale exception live forever.

dependabot-auto-merge.yml

  • Enables gh pr merge --auto --squash for patch and minor bumps of npm and maven dependencies only, expressed as an allow-list so anything unanticipated is excluded by construction.
  • github-actions bumps are deliberately excluded: they change which code CI itself executes, and auto-accepting an unreviewed SHA bump would undercut the whole reason those actions are pinned.
  • Ordering matters—--auto only queues the merge when required checks exist. Without branch protection it merges immediately, turning “auto-merge when green” into “merge unreviewed”.
