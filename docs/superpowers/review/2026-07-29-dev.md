# Developer Docs Site Review

**Date:** 2026-07-29
**Reviewed file:** `docs/index.html`
**Review goal:** Assess the page as the main architecture-oriented developer documentation for 2do AI.

## Scope Decision

The primary job of `docs/index.html` is to help a developer understand the product and its
architecture. Instructions for installing dependencies and running the projects locally belong in
the root `README.md`.

The architecture page may link to the README for setup, but should not duplicate its commands and
local-development instructions.

## Overall Assessment

The page is a strong backend architecture dossier, but not yet a complete architecture entry point
for the whole service.

- As an auth/backend architecture reference: approximately **8/10**.
- As the main architecture documentation page: approximately **5/10**.

Its strongest characteristic is the explicit distinction between implemented and planned behavior.
The same-origin rationale, session model, data diagrams, implemented flows, and deployment mechanics
are unusually clear.

The main opportunity is not adding more diagrams. It is rebalancing the page around:

1. the product's architectural drivers,
2. current versus target system state,
3. the responsibilities and boundaries of the major components,
4. the important architectural decisions and trade-offs,
5. links to deeper canonical documents.

## What Already Works Well

### Implemented versus planned

Green and yellow badges make it possible to document the current system and target architecture in
one place without presenting the roadmap as completed functionality. This convention should be
preserved and made even more systematic.

### Architecture rationale

The unified-origin deployment explanation clearly connects Cloudflare Pages, the `/api/*` reverse
proxy, Fly.io, in-memory sessions, and Neon autosuspend. It explains not only what was selected, but
why alternatives such as JWT or database-backed sessions were rejected.

### Backend behavior

The class and sequence diagrams provide useful implementation-level documentation for:

- registration,
- login and session creation,
- authenticated requests,
- logout,
- account deletion,
- category synchronization,
- AI memory and the LLM port.

### Delivery mechanics

The CI/CD section accurately documents path-filtered backend and frontend deployment workflows,
their different concurrency policies, and the backend rollback strategy.

### Low maintenance overhead

The single HTML file, embedded Mermaid diagrams, and lack of a documentation build tool are
appropriate for a solo, after-hours project. A heavier documentation framework is not currently
justified.

## Corrections Needed

### 1. Frontend status is inaccurate

`docs/index.html:57` says the SPA consumes the REST API, but the current `frontend/src/App.tsx` is
still the Vite demonstration application and has no API client.

`docs/index.html:82` calls the current frontend a React PWA, contradicting the correctly marked
planned PWA status in the Overview and the current roadmap.

Suggested current-state wording:

> React/Vite scaffold; `/api` development proxy and production reverse proxy are implemented.
> Product UI, API consumption, and PWA behavior are planned.

The current architecture diagram should say `React 19 static scaffold` or equivalent, not `PWA`.

### 2. The Overview's implemented badge covers planned product behavior

`docs/index.html:48` places an `implemented` badge beside an overview that describes the complete
intended product, including the three task layers and natural-rhythm reminders.

Split this into:

- **Product vision** — no implementation badge;
- **Current system state** — a compact capability/status table;
- **Target MVP state** — explicitly planned.

### 3. The audit-column rule is overstated

`docs/index.html:109-111` says every domain table has both `created_at` and `updated_at`.
`ai_memory_episode` is intentionally append-only and has no `updated_at`.

Suggested wording:

> Mutable domain tables use `created_at` and `updated_at`; append-only event tables may omit
> `updated_at`. Static reference tables may use a natural key and omit audit columns.

### 4. The verification label is confusing

The Overview says the documentation was verified against “backend commit `1fd0248`”, but that hash
is a documentation commit representing a repository snapshot rather than a backend-specific commit.

Use:

> Verified against repository snapshot `1fd0248` on 2026-07-29.

If retained, the drift command should cover all documented surfaces, not only
`backend/src/main/java`: frontend proxy/configuration, workflows, migrations, and foundation
documents can also invalidate the page.

### 5. Two Mermaid inheritance arrows are not validly escaped HTML

The `<|..` relations around `docs/index.html:192` and `docs/index.html:244` contain raw `<`
characters inside normal HTML `<pre>` elements. Browsers may recover, but an HTML validator reports
invalid markup.

Use `&lt;|..` in the HTML source.

## Information Architecture Improvements

The page currently moves from a short Overview directly into system diagrams and detailed backend
internals. It should first establish the forces that shaped the architecture.

Recommended order:

### 1. Product and architectural drivers

Explain concisely:

- the three planning horizons,
- why proactive natural-rhythm reminders are the differentiator,
- why persistent personal AI memory is required,
- the privacy and data-durability guardrails,
- the intended scale of 1-10 users and less than 1 QPS,
- how those constraints justify a deliberately small architecture.

Include one concrete end-to-end scenario, for example:

> A user records a long-term dream. The system retains it and relevant personal context. After a
> non-fixed interval, the backend selects it, asks the AI to formulate a contextual proposal, sends
> the proposal by email, and keeps it pending in the application until the user responds.

This gives the later diagrams a reason to exist.

### 2. Current system state

Add a capability matrix such as:

| Capability | Status | Main implementation |
|---|---|---|
| Persistence baseline | Implemented | Flyway, PostgreSQL, JPA validation |
| AI provider port | Implemented foundation | `LlmClient`, Spring AI adapter |
| AI memory aggregate | Implemented foundation | profile facts and episodes |
| Account and session auth | Implemented | Spring Security and server-side sessions |
| Categories | Implemented | seeded reference table and drift check |
| Product frontend | Scaffold only | React/Vite demo |
| Goals, dreams, tasks | Planned | S-02 and S-07 |
| Proactive proposal loop | Planned | S-04 and S-05 |
| PWA/offline behavior | Planned | S-10 |

This should be the authoritative quick answer to “what exists today?”

### 3. System context and container architecture

Keep the current and target system diagrams, but clarify the boundaries:

- browser/frontend,
- Cloudflare delivery and reverse proxy,
- Spring Boot API and background processing,
- PostgreSQL,
- external AI provider,
- future email provider,
- GitHub Actions as the delivery plane rather than runtime architecture.

The target diagram should include the email delivery provider because email is part of the MVP
proactive-return contract.

### 4. Code map

The current page documents backend classes in detail but does not give a balanced map of the
repository.

Add a short component table:

- `backend/.../user` — user aggregate and API;
- `backend/.../auth` — registration, request validation, error mapping;
- `backend/.../session` — explicit login/logout endpoints;
- `backend/.../security` — filter chain, CSRF, sessions, RFC 9457 security responses;
- `backend/.../account` — modular per-user erasure;
- `backend/.../category` — fixed life-domain reference data;
- `backend/.../ai` — provider-neutral LLM port and adapter;
- `backend/.../ai/memory` — personal AI-memory aggregate;
- `frontend/src` — current React scaffold and future product UI;
- `frontend/functions/api` — production same-origin reverse proxy;
- `context/foundation` — canonical product and architecture decisions.

File names shown on the page should be real relative links, not inert `<code>` text.

### 5. Architectural decisions and trade-offs

Create a compact decision register linking to the canonical sources:

- unified origin / no CORS,
- server-side session cookie rather than JWT,
- in-memory sessions on one Fly machine,
- Flyway schema ownership and `ddl-auto=validate`,
- expand-only database migrations,
- UUID v7 aggregate identifiers,
- provider-neutral `LlmClient`,
- structured profile plus episodic AI memory,
- PostgreSQL/Neon autosuspend,
- Polish-only category labels for MVP.

Each entry should contain the decision, why it was chosen, the main cost, and the condition that
would cause it to be revisited.

### 6. Behavioral flows

Retain the sequence diagrams, but group them more explicitly:

- **Identity and security flows**;
- **Data-integrity and erasure flows**;
- **AI/product flows**;
- **Operational flows**.

The current page contains considerably more detail about authentication than about the
differentiating product architecture. As S-02 through S-05 are implemented, the product flows
should become the prominent group and the Spring Security internals should become a deeper
subsection.

### 7. Data architecture

Keep the current and target ER diagrams. Add a short explanation of:

- aggregate ownership,
- user isolation,
- absence of `ON DELETE CASCADE`,
- how `PerUserDataDeleter` makes account erasure extensible,
- why episodes are append-only,
- which tables are current and which are placeholders or not yet designed.

### 8. Delivery and operations

Retain CI/CD and deployment, but state clearly:

- validation currently runs only on push to `master`;
- there is no pull-request validation workflow;
- tests therefore gate deployment after merge rather than gate merging;
- docs changes are not validated or deployed by either workflow;
- local-development instructions live in the root README;
- operational commands and incident steps live in `deployment-runbook.md`.

### 9. Roadmap and glossary

Keep both, but keep them summary-oriented and link to the PRD and roadmap as canonical sources.
Avoid copying detailed requirements into the HTML because duplication will drift.

## Navigation, Accessibility, and Responsive Design

### Progressive enhancement

Every section is initially `hidden`, and JavaScript reveals only the active section. If JavaScript
is disabled, blocked by content security policy, or fails to parse, the navigation remains visible
but the main content is blank.

This also limits browser search and printing to the currently visible section.

Preferred architecture for documentation:

- render all sections as normal HTML;
- use normal anchor navigation;
- optionally enhance navigation with JavaScript after the page loads;
- keep Overview visible by default if tab-like navigation remains;
- include a `<noscript>` fallback.

### Responsive layout

The page has a fixed 230px sidebar and large main padding without a media query. Add a narrow-screen
layout that turns the sidebar into a top navigation area or horizontally scrollable section list.

Verify at least:

- 320px phone width,
- 768px tablet width,
- a narrow desktop split-screen,
- 200% browser zoom.

### Navigation semantics

Add:

- a “Skip to main content” link;
- `aria-label="Documentation sections"` on `<nav>`;
- `aria-current="page"` on the active link;
- explicit hover and `:focus-visible` states;
- focus transfer to the new section heading after hash navigation, if the tab-like router remains.

### Tables and diagrams

Add:

- `<thead>` and `<tbody>`;
- `scope="col"` and `scope="row"` where applicable;
- captions for tables whose purpose is not obvious from the preceding heading;
- explicit `width` and `height` for SVG images;
- `loading="lazy"` for below-the-fold diagrams;
- textual summaries for complex diagrams rather than relying only on generic image alt text.

### CDN behavior

The Mermaid failure fallback is a good improvement, but the dependency should use an exact version
instead of mutable `@11`. Otherwise the rendered documentation can change without a repository
change.

If Mermaid remains on jsDelivr:

- pin an exact version;
- add a preconnect hint;
- show a short human-readable “diagram rendering unavailable” note before raw Mermaid source;
- make the prose independently sufficient to understand the architecture.

## Discoverability and Hosting

The approved design explicitly chose repository-local viewing and excluded GitHub Pages. That was
reasonable for the original task, but “main docs page” creates a discoverability requirement.

For now:

- create or update the root `README.md` to link prominently to `docs/index.html`;
- let the README own prerequisites, local startup, tests, and developer commands;
- let `docs/index.html` own architecture;
- link back to the README from the architecture page.

If the documentation is hosted later, remember that `docs/index.html` is only a single-file shell,
not a self-contained artifact: it depends on Mermaid from a CDN and SVG files under
`context/foundation/`. A deployment must publish those assets with compatible relative paths.

## Maintenance Recommendations

Continue hand-editing the page, but add a small deterministic verification check rather than a
documentation framework.

Useful checks:

- every navigation hash resolves to a documentation section;
- all relative links and image paths exist;
- HTML validation catches unescaped Mermaid syntax;
- every Mermaid block renders without an error;
- an invalid hash falls back to Overview;
- CDN failure leaves prose visible;
- JavaScript failure or disablement still leaves useful content;
- representative mobile and desktop widths have no horizontal page overflow;
- implemented/planned badges remain present where target behavior is described.

Documentation freshness should be recorded as a repository snapshot and checked against all
documented surfaces. Manual status labels should be reviewed whenever a feature slice is archived
or merged.

## Recommended Success Test

After the changes, a developer who spends five minutes on `docs/index.html` should be able to
answer:

1. What user problem makes 2do AI different from a conventional todo application?
2. Which parts exist today and which remain planned?
3. What are the runtime components and how does a request move through them?
4. Why are sessions in-memory and why is production same-origin?
5. Where do account data, AI memory, categories, and future tasks belong?
6. How is the system tested, deployed, and rolled back?
7. Which document is authoritative for product requirements, data design, deployment operations,
   and local startup?

If those answers are easy to find without reading every class diagram, the page is serving its
architecture-first purpose.
