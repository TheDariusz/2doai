## Sanitize stored content before injecting it into an LLM prompt

- **Context**: AiMemoryRenderer (AiMemoryRenderer.java:80), and any future renderer, concatenates stored aggregate content — Episode.payload, profile facts — into a block fed to an LLM as system/context content (S-04 onward).
- **Problem**: Stored values originate (directly or indirectly) from user-influenced data. Concatenated verbatim into a prompt, a crafted payload can carry instructions into the model's context — a stored / second-order prompt-injection vector. The render seam is the natural choke point.
- **Rule**: Before any stored, user-influenced content reaches an LLM prompt, neutralize it at the render boundary — fence/delimit untrusted segments (wrap payloads in a clearly-marked data block the model is told to treat as data, not instructions) and/or strip control directives. Never concatenate raw stored content straight into prompt text.
- **Applies to**: Any code rendering persisted / user-influenced data into an LLM request (memory rendering, RAG context assembly, tool outputs). First live in S-04 (proposals) and S-09 (auto-tag).

## Let a scale-to-zero database actually sleep — idleness is the cost lever

- **Context**: Prod Postgres is Neon Free (100 CU-hours per project per month; compute autosuspends after ~5 min of inactivity; autoscaling to 2 CU cannot be capped on Free) sitting behind an always-on Fly machine (`auto_stop_machines = "off"`, `min_machines_running = 1`, required by the FR-011 scheduler). F-02 introduced the first datasource, so from that point the backend holds a Hikari pool open 24/7.
- **Problem**: Hikari's defaults are tuned for a flat-billed database and silently defeat autosuspend two ways: `minimum-idle` defaults to `maximum-pool-size` (connections pinned open forever), and **`keepalive-time` defaults to 120s in HikariCP 6** (shipped with Boot 4) — a real ping every 2 minutes, which resets Neon's 5-minute idle timer before it can ever fire. The compute therefore never suspends: ~730 h/month × 0.25 CU ≈ **183 CU-h against a 100 CU-h budget**, exhausted in ~2–3 weeks with essentially zero traffic. Exhaustion is not a soft throttle — Neon *refuses new connections* until the monthly reset, and because Flyway gates startup, the app then **cannot boot at all**. That converts any routine restart (OOM-kill on the 512 MB machine, Fly host migration) from a self-healing 30-second blip into a hard outage — and Fly never notices, because it probes `/actuator/health/liveness` while `db` lives in the readiness group.
- **Rule**: On a metered, scale-to-zero database, **idle time is billed unless you actively give it up**. (1) The pool must drain: `minimum-idle=0`, a short `idle-timeout`, and `keepalive-time=0` — never enable keepalive to "fix" stale connections. (2) **Nothing may touch the DB more often than the autosuspend window (~5 min)** — anything more frequent pins the compute awake permanently, regardless of user count or data size. Free-tier viability is a function of idleness, not of traffic. (3) The always-on JVM is the scheduler; the database is only the store — hold timing state in memory and touch Postgres only when actually doing work.
- **Applies to**: Above all **S-05 (natural-rhythm scheduler)** — a `@Scheduled` poll on any interval ≤5 min blows the budget on its own; compute the next fire time in memory and hit the DB only when firing (~1 per 2–7 days). Also any future health poll, cache warm-up, or cron; the append-only `ai_memory_episode` log versus the 0.5 GB Free storage cap; and the "budget ~€3–6/mo Fly + Neon free/**idle** tier" assumption in `infrastructure.md`, which only holds if idle is real. Enforced by `DataSourcePoolPropertiesTest` + the comment block in `application.properties`.

### Correction (2026-07-22) — moved off Free onto paid Launch, PG 17 → 18

The entry above describes the setup as **Neon Free** (100 CU-hour monthly quota; autoscaling to 2 CU that "cannot be capped on Free"). That premise is **no longer current**, but the rule it teaches is unchanged and, if anything, more important now.

- **What changed**: Prod is now a **paid Launch** plan on a **new project** (`2doai` / `delicate-violet-02960517`), created to move Postgres **17 → 18** — Neon has no in-place major upgrade, so 17 → 18 meant a fresh project + repointing the three `SPRING_DATASOURCE_*` Fly secrets. No data migrated: Flyway V1–V3 rebuild the schema and re-seed `category`. The old PG 17 project (`sparkling-mode-02463213`) was deleted after cutover. Compute floor was cut **1 ↔ 4 CU → 0.25 ↔ 1 CU** (the autoscaling *minimum* is billed for every second a connection is open, so this is a 4× reduction on idle billing; the 1 CU max is now a hard cap, not the uncappable 2 CU of Free).
- **What the correction is**: There is no longer a 100 CU-hour quota, and therefore **no hard cutoff** — the old "quota exhausted → Neon refuses connections → Flyway gates startup → app can't boot" failure mode is gone. In its place: overrunning idle just **quietly raises the bill**, with nothing to alert you. On paid, sloppy idleness is arguably *worse* to catch because the loud failure that used to expose it no longer fires.
- **What is unchanged (the actual lesson)**: The cost lever is still **idleness**, and the single quantity that must stay rare is a **database query** — each one resets Neon's ~5-min idle timer, and anything querying more often than that pins the compute awake 24/7 (~730 h × 0.25 CU ≈ **183 CU-h/month**) regardless of user count or data size. The Hikari drain, the liveness-only Fly probe (`db` lives in readiness, never touch it from a probe), and the S-05 "compute next fire time in memory, query only when firing" rule all still hold verbatim. The trade is a ~1s Neon cold-start on the first request after idle — the correct price of a sleeping database at MVP scale.
- **JDBC gotcha (found during cutover)**: the Fly `SPRING_DATASOURCE_URL` must be `jdbc:postgresql://<pooler-host>/neondb?sslmode=require` — **strip Neon's `channel_binding=require`**, which is libpq-only. pgjdbc forwards unknown URL params to the server as startup options and the connection fails.
- **Stale references to fix opportunistically**: `infrastructure.md` still frames the budget as "Fly + Neon free/idle tier"; that's now "Fly + Neon paid Launch, kept cheap by idleness." Update if/when that file is next touched.
